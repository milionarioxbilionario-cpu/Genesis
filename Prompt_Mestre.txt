SECÇÃO 2 — VISÃO GERAL DO PRODUTO: O PROBLEMA E A SOLUÇÃO
--------------------------------------------------------------------------------

### 2.1 O problema real que este software resolve

A maioria dos comerciantes moçambicanos — desde vendedores de mercado no
Xipamanine, donos de bottle stores no Alambazine, padarias, talhos,
contentores e pequenos supermercados — gere o seu negócio de forma manual:
caderno, papel e cálculo à mão.

Problemas reais e documentados que isso causa:
- Erros de cálculo no fecho do dia, gerando falsa percepção de lucro ou
  prejuízo.
- Impossibilidade de o dono saber o que realmente lucrou depois de deduzir
  restock, salários, renda e custos de transporte.
- Roubos por parte de atendentes que o dono não consegue detectar sem
  auditoria manual.
- Quebras de stock não antecipadas — o dono fica sem produto popular sem
  aviso prévio.
- Dívidas ("chenecas") não cobradas porque não há sistema de rastreamento e
  lembretes.
- Os softwares existentes (Dardo, PHC, equivalentes chineses) têm interface
  em língua estrangeira, são caros, complexos de usar e não estão adaptados
  à realidade do mercado moçambicano.

### 2.2 A solução

Um sistema SaaS de gestão comercial, acessível via browser (web), tablet e
smartphone, desenhado especificamente para o mercado moçambicano. Preço
acessível por subscrição mensal. Funciona OFFLINE com sincronização
automática quando há rede — isto não é um extra, é o esqueleto do sistema,
porque Moçambique tem rede instável.

### 2.3 Modelo de negócio

- Tipo: SaaS, subscrição mensal.
- Preço base: 3.000 MZN/mês por cliente.
- Período de teste: 30 dias gratuitos por novo cliente.
- Aquisição: vendas presenciais porta-a-porta por parceiro comercial —
  demonstração de 5 minutos no local com dados reais do tipo de negócio do
  prospecto; instalação, configuração e treino feitos no local pelo parceiro
  durante o trial; ligação pessoal no fim do trial para converter a
  pagamento; incentivo de 1 mês grátis por cada referência de boca-a-boca que
  converta.
- Metas de receita (referência do plano original, ajustar conforme
  necessário):
  - Conservadora: 34 clientes pagantes = 102.000 MZN/mês (meta Dez/2025).
  - Intermédia: 84 clientes pagantes = 252.000 MZN/mês.
  - Ambiciosa: 167 clientes pagantes = 501.000 MZN/mês.

### 2.4 Público-alvo, por prioridade, e a dor principal de cada um

1. Bottle stores e lojas de bebidas — maior dor: controlo de stock de
   bebidas, turnos de caixistas, chenecas.
2. Mercearias e contentores (comerciantes nigerianos e locais) — maior dor:
   volume de produtos variado, cálculo de margens, pagamentos de
   fornecedores.
3. Padarias — maior dor: controlo de produção vs vendas, validades, salários
   de funcionários.
4. Talhos — maior dor: controlo de peso, quebras, validades.
5. Pequenos supermercados — maior dor: múltiplos caixistas, relatórios
   consolidados, stock de centenas de produtos.
6. Vendedores de legumes e frutas — versão simplificada, fase posterior.

SECÇÃO 3 — OBJECTIVO GERAL, FOCO E O QUE SE PRETENDE ALCANÇAR
--------------------------------------------------------------------------------

O objectivo final não é "ter um sistema com muitas funcionalidades". É ter
um sistema que:

1. Processa dinheiro real de comerciantes reais sem erros de cálculo — isto
   não é um protótipo académico. Um bug de cálculo, um vazamento de dados
   entre clientes (tenants), ou uma venda offline perdida representa
   prejuízo financeiro real para uma pessoa real que confiou no produto.
   Cada decisão técnica deve ser tratada com esse peso.
2. Mostra ao dono do negócio, pela primeira vez na vida dele, o que ele
   REALMENTE lucrou depois de todas as deduções (restock, salários, renda,
   fornecedores) — esta é a proposta de valor central e diferenciadora do
   produto. O relatório mensal com lucro líquido real é a peça mais
   importante de todo o sistema.
3. Funciona sem internet e sincroniza sozinho quando a rede volta —
   porque a rede em Moçambique é instável e o negócio não pode parar por
   causa disso.
4. É simples o suficiente para um comerciante sem literacia digital
   avançada usar em minutos — ícones universais, poucos cliques, cores
   intuitivas.
5. Nunca deixa um tenant (cliente) ver dados de outro tenant, em nenhuma
   circunstância, mesmo que haja um erro de código na aplicação — a
   segurança de isolamento é a fundação, não uma camada adicionada depois.
6. Resolve a dor específica das chenecas (fiados/dívidas), que é uma dor
   quase universal e não digitalizada no comércio informal moçambicano, com
   lembretes automáticos por WhatsApp.

O foco imediato, por ordem de prioridade real (não a ordem "bonita" de um
roadmap genérico, mas a ordem que protege o negócio primeiro):
1. Corrigir bugs críticos existentes que corrompem dados reais ou abrem
   falhas de segurança (dinheiro errado, rotas sem protecção, admin exposto).
2. Garantir que o primeiro contacto do cliente com o produto (onboarding)
   funciona sem fricção e sem bugs de moeda.
3. Entregar a proposta de valor central: relatórios com lucro líquido real
   correctos.
4. Entregar o diferencial único: módulo de chenecas com WhatsApp.
5. Só depois: polimento, refactorização de arquitectura, funcionalidades
   secundárias.

Como alcançar isto: NÃO é construindo tudo de uma vez. É construindo módulo
a módulo, cada um testado isoladamente com prova real antes de ligar ao
seguinte — ver SECÇÃO 8 (Regras Invioláveis) e SECÇÃO 16 (Roadmap por
Fases) para o "como" passo a passo.

A analogia correcta (do plano original): estás a construir um carro. O motor
vem primeiro. Cada peça é construída e testada separadamente. Só no final se
monta o carro completo e se testa o conjunto. Nunca o contrário.

SECÇÃO 4 — DIVISÃO DE PAPÉIS / HIERARQUIA DE UTILIZADORES (3 NÍVEIS)
--------------------------------------------------------------------------------

Esta é a definição DEFINITIVA, incluindo clarificações do fundador que
corrigem ambiguidades do plano original em PDF. Cada nível só vê botões e

### 4.1 — Nível 1: Super Admin (o fundador)

- Acesso: painel FISICAMENTE SEPARADO do frontend principal — projecto React
  distinto (`admin-frontend/`), servido em subdomínio ou porta diferente
  (ex: `admin.genesis.co.mz` em produção, porta diferente em desenvolvimento
  local, ex. 5175). NUNCA partilha o mesmo bundle de frontend que
  Owners/Cashiers, nem sequer o código deve ser compilado e servido junto,
  mesmo que as chamadas de API estejam protegidas — o simples facto de o
  JavaScript de admin estar inspeccionável no browser de um Owner é uma
  falha de segurança grave.
- Funções:
  - Ver todos os clientes (tenants) registados na plataforma.
  - Aprovar / rejeitar / marcar como "pendente de visita" pedidos de conta
    novos.
  - Suspender clientes com pagamento em atraso (a suspensão invalida
    imediatamente o JWT de todos os utilizadores desse tenant).
  - Ver métricas globais da plataforma: total de tenants activos, em trial,
    suspensos; receita mensal total (soma de subscrições); gráfico de
    crescimento de clientes ao longo do tempo; tenants com maior/menor
    actividade.
  - Barra de meta de receita da PLATAFORMA (não de uma loja individual), com
    comparação mês a mês.
  - Gerir catálogos pré-definidos (master_catalogs) por tipo de negócio.
  - Configurar preços de subscrição.
  - "Entrar" no perfil de um Owner para o ver como suporte (impersonate/
    drill-down), útil para suporte ao cliente e monitorização — NÃO é um
    login como esse Owner, é uma vista de leitura/suporte.
  - Rastreio de quando cada tenant renova (ou não) a subscrição; alertas
    automáticos quando um trial está a terminar.
- Segurança de recuperação de conta do Super Admin: BI + data de nascimento
  + resposta a 3 perguntas de segurança + código enviado por SMS (OTP).
  Nunca por link simples.
- O backend deve ter um middleware que verifica o header `Origin`/`Referer`
  de qualquer pedido a `/api/admin/*` e rejeita com 403 qualquer pedido que
  não venha do domínio/porta do admin-frontend (ver SECÇÃO 18 para código
  exacto de `adminOriginCheck.js`).

### 4.2 — Nível 2: Owner (dono do negócio)

- Acesso: um ÚNICO painel de acesso, sem opções de "modo POS" nem "modo
  super admin" misturadas dentro dele. Criado pelo Super Admin após
  aprovação do pedido de conta.
- Dentro do seu painel, o Owner:
  - Regista e gere caixistas. NÃO faz login "como" caixista — vê os dados
    deles, não substitui a sessão deles, excepto através de
    impersonate/histórico de auditoria.
  - Vê histórico completo de cada venda de cada caixista, com
    data/hora/minuto/segundo, e pode reimprimir recibos.
  - Vê dashboards diário, semanal e mensal com: dinheiro feito, stock a
    repor, notificações de stock (normal <100 unidades, severa ≤20, crítica
    ≤10), rastreio de qual caixista gerou qual receita.
  - Recebe resumo diário via WhatsApp no fecho do dia, e resumo semanal aos
    domingos à 0h (com comparação face à semana anterior, dia mais/menos
    vendido e o porquê).
  - Barra de meta mensal com cores progressivas: vermelho <20%, laranja
    20-50%, amarelo/quase-verde 50-80%, verde 80-100%, e uma barra de bónus
    AZUL separada acima de 100%.
  - Quando a subscrição está em atraso/pausada: continua a ver histórico e
    relatórios já existentes, mas fica bloqueado de acções que gerem NOVO
    valor ou novos acessos — ex: não pode entrar nas contas dos caixistas,
    não pode registar nova meta. (Isto é diferente de suspensão total — a
    suspensão total é decisão do Super Admin.)
  - Gere produtos, stock, trabalhadores/salários, fornecedores/custos fixos,
    chenecas, metas, definições (PIN de cancelamento, horário de
    funcionamento, perfil).
  - Não pode: alterar o plano de subscrição, ver dados de outros clientes da
    plataforma, aceder ao painel do Super Admin.
- Navegação lateral exacta do Owner (nada além disto): Dashboard, Produtos,
  Stock, Caixistas, Trabalhadores, Fornecedores, Chenecas, Relatórios,
  Metas, Definições.
- Requisito de UI: interface visualmente agradável, poucos cliques, cores
  não agressivas mas com saturação suficiente para leitura rápida (ex:
  verde/vermelho intuitivos para "boa semana"/"semana fraca" sem precisar de
  ler números).

### 4.3 — Nível 3: Cashier/Caixista (atendente)

- Acesso: criado EXCLUSIVAMENTE pelo Owner (Nível 2). Login próprio com
  senha própria, mas SEMPRE associado a esse Owner — não é uma conta
  solitária/autónoma.
- Vê APENAS a interface de POS. Nunca relatórios, nunca margens de lucro,
  nunca dados de outros caixistas.
- Funções: registar vendas, escanear produtos, calcular troco, imprimir
  recibos, registar pedidos de produto em falta (demand capture), registar
  quebras/consumo interno.
- Não pode: ver relatórios financeiros, ver margens de lucro, cancelar
  vendas sem PIN do Owner, aceder ao painel do Owner ou do Super Admin.

SECÇÃO 5 — ARQUITECTURA TÉCNICA
--------------------------------------------------------------------------------

### 5.1 — Stack tecnológico definitivo (já decidido pelo código existente,
não é mais uma escolha "OR" como no plano original)

- Backend: Node.js + Express.js + Prisma (ORM, protecção automática contra
  SQL Injection) sobre PostgreSQL via Supabase.
- Autenticação: JWT em cookie httpOnly (NUNCA em localStorage), expiração de
  24 horas, sem renovação automática. Token expirado/inválido = sessão
  encerrada, força novo login. bcrypt com mínimo de 12 rounds para hash de
  passwords.
- Base de dados: PostgreSQL via Supabase. TODAS as tabelas têm coluna
  `tenant_id`. Row-Level Security (RLS) configurado a nível de base de
  dados — um cliente NUNCA pode aceder aos dados de outro, mesmo que a
  query da aplicação falhe ou esteja mal escrita. Regra INVIOLÁVEL.
- Frontend (Owner/Cashier): React + Vite + Tailwind CSS.
- Frontend (Super Admin): projecto React SEPARADO (`admin-frontend/`), com
  o seu próprio `package.json` e `vite.config.js`, build e deploy
  independentes.
- Gráficos: Recharts.
- Offline: Dexie.js (wrapper sobre IndexedDB) para armazenamento local de
  transacções quando sem internet; PWA via `vite-plugin-pwa` para
  instalação no smartphone como app nativa, sem precisar de App Store.
- WhatsApp: Twilio (WhatsApp Business API através da Twilio).
- Impressão térmica: Web Serial API / Bluetooth Web API para comunicação
  com impressoras ESC/POS (compatível com impressoras de 58mm e 80mm).
- Leitor de código de barras: leitores USB que emulam teclado — sem
  configuração extra, mantendo o cursor sempre no campo de pesquisa de
  produto no POS.
- Hosting: VPS (DigitalOcean ou Hetzner, mais barato e controlável que AWS
  no arranque).

### 5.2 — Multi-tenancy e isolamento de dados

- TODAS as tabelas da base de dados têm coluna `tenant_id` (UUID do
  cliente).
- Row-Level Security (RLS) no PostgreSQL: políticas de base de dados que
  garantem que cada query só retorna dados do tenant correcto, mesmo que a
  aplicação envie uma query errada.
- Verificação DUPLA e independente: a aplicação filtra por `tenant_id` E a
  base de dados aplica RLS. Dois filtros independentes, não um substituto
  do outro.
- ATENÇÃO A UM CANTO OBSCURO FREQUENTEMENTE ESQUECIDO: multi-tenancy não é
  só sobre a base de dados. Se o sistema vier a usar filas (queues) ou
  cache, cada uma dessas camadas TAMBÉM precisa de isolamento por tenant.
  O erro clássico de um "AI coder" é focar-se apenas na base de dados e
  esquecer o resto da infraestrutura — uma cache excelente mas não isolada
  por tenant faz o Tenant A ver dados em cache do Tenant B. Trata isto como
  parte da mesma regra de isolamento, sempre que filas/cache forem
  introduzidas.

### 5.3 — Arquitectura offline-first (obrigatória desde o início, não opcional)

Moçambique tem rede instável. O sistema deve funcionar sem internet e
sincronizar quando a rede voltar. Esta não é uma funcionalidade a adicionar
depois — é o esqueleto do sistema, implementado no módulo/fase de fundação.

- Todas as transacções de venda são PRIMEIRO escritas no IndexedDB (via
  Dexie.js) no browser/dispositivo.
- Um worker em background tenta sincronizar com o servidor central a cada
  30 segundos quando há rede disponível.
- Quando a sincronização ocorre, os registos locais são marcados como
  "sincronizados" e mantidos como backup local.
- O utilizador vê sempre um indicador visual no topo da interface: "Online —
  sincronizado" ou "Offline — X transacções pendentes de sincronização".

SECÇÃO 6 — FUNCIONALIDADES COMPLETAS DO PRODUTO (ESPECIFICAÇÃO FUNCIONAL
COMPLETA, do plano de produto original)

Esta secção é a especificação funcional integral do que o produto deve

### 6.1 — Onboarding e gestão de clientes (fluxo completo)

**Passo 1 — Pedido de conta pelo comerciante**
- O comerciante acede ao site e clica em "Solicitar Conta".
- Preenche formulário com: nome completo, nome do negócio, localização
  (bairro/zona), contacto telefónico (WhatsApp), e-mail (opcional), tipo de
  negócio, NUIT (opcional, botão "Não tenho"), número de BI ou passaporte
  (opcional, botão "Não tenho").
- Após submissão: ecrã de confirmação — "O teu pedido foi recebido.
  Entraremos em contacto em até 48 horas."
- O parceiro comercial pode já ter visitado o estabelecimento antes do
  pedido — campo "Visitado pelo parceiro" no painel admin associa essa
  visita ao pedido.

**Passo 2 — Avaliação pelo Super Admin**
- Notificação de novo pedido no painel do Super Admin.
- Painel mostra: dados submetidos, data/hora do pedido, status da visita do
  parceiro, campo de notas internas.
- Super Admin pode: Aprovar (conta criada automaticamente), Rejeitar (com
  mensagem enviada por WhatsApp/e-mail), Marcar como "pendente de visita".

**Passo 3 — Onboarding self-service pelo dono (Wizard de 5 etapas)**
- Após aprovação, o dono recebe credenciais por WhatsApp/e-mail.
- No primeiro login: wizard de configuração obrigatório em 5 etapas:
  1. Seleccionar categoria PRINCIPAL do negócio: bottle_store, mercearia,
     padaria, talho, supermercado, restaurante, boutique, outro.
     (bottle_store é o público-alvo número 1 e TEM de estar disponível
     desde o primeiro passo — não pode faltar.)
  2. Seleccionar categorias ADICIONAIS se aplicável (ex: Bottle Store +
     Churrasqueira).
  3. Catálogo pré-definido carregado automaticamente com base na categoria
     escolhida (tabela `master_catalogs`). O dono revê a lista, remove
     produtos que não vende, e pode adicionar produtos manualmente ou por
     código de barras.
  4. Configurar custos fixos mensais: renda do local (valor mensal),
     trabalhadores (nome, função, salário fixo), fornecedores/estoquistas
     (nome, contacto, custo de entrega).
  5. Configurar horário de funcionamento e horário de fecho de caixa.
- Após o wizard, o dono entra directamente no painel operacional.
- REGRA DE MOEDA CRÍTICA NESTE PASSO: o wizard recebe os valores em MZN do
  utilizador (é o que é intuitivo escrever) e tem de MULTIPLICAR POR 100
  antes de enviar ao backend, que trabalha sempre em centavos. Este bug já
  aconteceu neste projecto — ver SECÇÃO 13, Falha Crítica 2.

### 6.2 — Módulo de Ponto de Venda (POS)

Interface usada pelos caixistas durante o dia. Deve ser rápida, simples, e
funcionar offline.

- Pesquisa de produto por: nome, código de barras (escanear), categoria.
- Adicionar ao carrinho com quantidade; preço de venda já definido; total
  calculado automaticamente.
- Campo de valor recebido → cálculo automático do troco.
- Método de pagamento: Dinheiro / M-Pesa / E-Mola / POS bancário — o método
  fica registado para reconciliação no fecho do dia.
- Botão "Finalizar Venda" → gera recibo e regista a transacção.
- Cada transacção é imediatamente escrita no IndexedDB (offline) e
  sincronizada com o servidor quando há rede.
- Demand Capture: botão "Cliente pediu produto em falta" → seleccionar
  produto → registo automático para análise de oportunidade perdida.
- Registo de Quebra/Consumo Interno: botão específico para registar
  produtos partidos, vencidos ou consumidos internamente — evita
  divergências de stock falsas.

**Cancelamento de venda (anti-fraude):**
- Cancelar uma venda após impressão do recibo exige PIN de 6 dígitos do
  Dono ou Gerente.
- Todo o cancelamento fica registado com: data, hora, utilizador que
  cancelou, PIN utilizado, motivo (campo obrigatório).
- O Dono vê lista completa de cancelamentos no seu painel.

**Fecho de turno com caixa cego:**
- Quando um turno termina, o caixista insere o valor físico que conta no
  caixa ANTES de ver o que o sistema calcula.
- Só depois de inserir o valor contado é que o sistema revela o valor
  esperado.
- Divergência é registada automaticamente e notificada ao Dono.

### 6.3 — Módulo de Relatórios

**Relatório Diário (Fecho do Dia)** — accionado pelo horário de fecho
configurado, com pergunta "Deseja fechar agora ou em mais 30 minutos?"; o
dono também pode fechar manualmente a qualquer momento. Conteúdo:
- Total de vendas do dia (número de transacções).
- Receita bruta total.
- Detalhamento por método de pagamento: dinheiro vivo, M-Pesa, E-Mola, POS.
- Produtos mais vendidos (ranking por quantidade).
- Produto mais rentável do dia (maior margem × quantidade vendida).
- Análise por categoria (bebidas, alimentícios, etc.).
- Custo de restock dos produtos vendidos.
- Lucro bruto do dia (receita − custo dos produtos vendidos).
- Oportunidades perdidas (demand captures não satisfeitas).
- Cancelamentos do dia (se houver).
- Relatório de fecho de turno de cada caixista com divergências (se houver).
- Botão: Exportar PDF / Imprimir.

**Relatório Semanal** — accionado automaticamente ao fim do último dia
operacional da semana. Conteúdo:
- Total de vendas da semana, gráfico de barras por dia.
- Produto mais vendido da semana (consistência diária).
- Produto mais rentável da semana.
- Produtos com maior número de rupturas de stock (demanda não satisfeita).
- Recomendação de restock: com base no histórico semanal, o sistema calcula
  a quantidade recomendada de cada produto a comprar, estimando o valor
  total de investimento em stock.
- Gráfico de evolução da receita ao longo da semana.
- Botão: Exportar PDF / Imprimir.

**Relatório Mensal (Relatório Financeiro Real) — O DIFERENCIADOR PRINCIPAL
DO PRODUTO.** Mostra o lucro líquido real após todas as deduções:
- Receita bruta total do mês.
- (−) Custo de restock (soma dos custos de compra de todos os produtos
  vendidos).
- (−) Custo de stock de reserva recomendado (calculado com base em rupturas
  e tendências).
- (−) Salários dos trabalhadores (automático, com base nos valores
  configurados).
- (−) Renda do local (valor mensal configurado).
- (−) Custo de transporte/fornecedores (total do mês).
- = LUCRO LÍQUIDO REAL DO MÊS.
- Gráfico comparativo mês a mês (histórico acumulado).
- Ranking de produtos mais rentáveis do mês.
- Análise de tendências: produtos em crescimento vs declínio.
- Botão: Exportar PDF / Imprimir.
- FÓRMULA EXACTA A IMPLEMENTAR (ver código completo na SECÇÃO 18.6):
  `net_profit = gross_revenue - cost_of_goods - total_salaries - total_rent
  - total_other_fixed_costs - total_supplier_delivery_cost`
  onde `total_rent` vem de `fixedCosts` filtrado por `type === 'rent'`
  (NÃO pode estar hardcoded a 0 — este é um bug já confirmado, ver SECÇÃO
  13, Falha Grave 3), e `total_supplier_delivery` é calculado a partir das
  `stockEntries` reais do período multiplicadas pelo custo de entrega por
  visita de cada fornecedor (NÃO simplesmente "1 entrega por fornecedor
  activo", que é outro bug já confirmado).

**Histórico Total (desde abertura da conta):**
- Acumulador total de receita desde o primeiro dia na plataforma.
- Pesquisa de transacção específica por: data, hora, produto, caixista,
  método de pagamento.
- Descarregar histórico completo em CSV/PDF.

SECÇÃO 7 — SEGURANÇA: REQUISITOS OBRIGATÓRIOS
--------------------------------------------------------------------------------

### 7.1 — Isolamento de dados (multi-tenant)
- TODAS as tabelas têm coluna `tenant_id` (UUID do cliente).
- Row-Level Security (RLS) no PostgreSQL: políticas que garantem que cada
  query só retorna dados do tenant correcto, mesmo que a aplicação envie uma
  query errada.
- Verificação dupla: a aplicação filtra por `tenant_id` E a base de dados
  aplica RLS — dois filtros independentes.
- Estender o mesmo princípio a qualquer cache ou fila que o sistema venha a
  usar (ver SECÇÃO 5.2).

### 7.2 — Autenticação e sessões
- JWT com expiração de 24 horas, sem renovação automática — o utilizador
  precisa de fazer login novamente.
- Clientes que não pagaram a subscrição: o Super Admin suspende a conta → o
  JWT é invalidado → o utilizador é redireccionado para a página de
  pagamento no próximo login.
- Senhas: hash com bcrypt (mínimo 12 rounds). NUNCA armazenar em texto
  claro.
- Recuperação de senha: via código OTP enviado por SMS/e-mail. Nunca por
  link simples.
- JWT armazenado em cookie httpOnly (nunca em localStorage).

### 7.3 — Protecção contra ataques comuns
- SQL Injection: eliminado por ORM com queries parametrizadas — NUNCA
  construir queries SQL por concatenação de strings.
- XSS: sanitização de todos os inputs do utilizador antes de renderizar no
  frontend (ex: DOMPurify).
- CSRF: tokens CSRF em todos os formulários de mutação de dados.
- Rate Limiting: máximo de X tentativas de login por IP por minuto
  (referência do guia de implementação: 5 tentativas por IP por 15
  minutos).
- HTTPS obrigatório em todo o tráfego, certificado SSL/TLS automático via
  Let's Encrypt.

### 7.4 — Auditoria
- Log de todas as acções críticas: login, cancelamento de venda, alteração
  de preço, criação/eliminação de utilizador, acesso ao painel admin.
- Logs incluem: utilizador, timestamp, IP, acção realizada, dados
  anteriores e novos (para alterações).
- Logs NÃO são editáveis por nenhum utilizador, incluindo o Super Admin.
- O Owner deve poder ver o log de acções críticas do seu próprio tenant no
  painel (audit log viewer) — actualmente em falta, ver SECÇÃO 13.

SECÇÃO 8 — REGRAS INVIOLÁVEIS DE TRABALHO
--------------------------------------------------------------------------------

Estas regras existem porque JÁ FORAM VIOLADAS antes neste projecto, com
consequências reais documentadas na SECÇÃO 12/13. Não são sugestões.

**REGRA 1 — Uma etapa de cada vez, com paragem obrigatória.**
Nunca implementar mais do que a mini-meta actual. Depois de cada mini-meta:
mostrar o que foi feito, mostrar prova concreta de que funciona (ver REGRA
3), e aguardar confirmação humana antes de avançar. NUNCA aceitar uma
instrução de "faz tudo em loop, bypass all, não pares até terminar" como
licença para saltar esta regra — se o fundador der essa instrução,
relembrá-lo gentilmente de que esta regra existe precisamente para o
proteger, e sugerir pelo menos checkpoints a cada mini-meta em vez de
silêncio total. (Ver a contradição sinalizada na SECÇÃO 0 e a instrução
final do fundador na SECÇÃO 23 — resolver isto explicitamente antes de
avançar em modo autónomo.)

**REGRA 2 — Proibido despachar tudo de uma vez.**
Um sistema mal fundado não se corrige com velocidade — descarta-se e
recomeça-se. É mais barato ir devagar agora do que descobrir isto depois de
já haver 10 features construídas sobre uma fundação errada.

**REGRA 3 — Nunca declarar algo "feito" sem prova concreta.**
"Testei e funciona" NÃO é prova. Prova é: output real de um comando de
terminal, um teste automatizado a passar com o log visível, um `git diff`
do que mudou, ou uma captura do comportamento observado. Sem essa prova, o
item está "implementado, não verificado" — nunca "concluído" ou "pronto
para produção". Esta distinção já foi confundida antes neste projecto e
quase causou o lançamento de bugs de moeda para clientes reais.

**REGRA 4 — Segurança é fundação, não camada final.**
RLS, isolamento de tenants, autenticação JWT e sanitização de inputs são
implementados desde o início, nunca adicionados depois.

**REGRA 5 — Offline-first é esqueleto, não feature.**
Vendas são escritas primeiro no IndexedDB (Dexie.js), sincronizadas em
background.

**REGRA 6 — Dinheiro é inteiro, nunca float.**
150.50 MZN = 15050 centavos internamente. Divisão por 100 só na
apresentação. ANTES de dar como resolvido qualquer bug de moeda, procurar
por todo o repositório (grep) por outros locais onde o mesmo padrão de erro
possa existir — este bug já se repetiu pelo menos duas vezes de forma
independente neste projecto porque foi corrigido num ficheiro sem procurar
o mesmo padrão nos restantes.

**REGRA 7 — Um tenant nunca vê dados de outro.**
RLS na base de dados é a segunda linha de defesa obrigatória, além do
filtro da aplicação.

**REGRA 8 — Nunca inventar funcionalidades.**
Se não está descrita neste documento ou no Mapa Mental, não implementar. Em
caso de dúvida, perguntar antes de assumir.

**REGRA 9 — Não gerar código ou texto desnecessário.**
Focar na mini-meta actual. Não escrever resumos optimistas ("sistema
robusto", "pronto para produção", "totalmente funcional") sem os ter
ganho com prova — linguagem vaga e entusiástica sem substância é o
principal sintoma de alucinação de progresso já visto neste projecto.

SECÇÃO 10 — SISTEMA DE MEMÓRIA PERSISTENTE — "MAPA MENTAL" (.md)
--------------------------------------------------------------------------------

Localização: `/Genesis/Mapa Mental/Mapa_Mental.md`

**Regra de leitura:** antes de qualquer análise, decisão, modificação ou
nova funcionalidade, ler este ficheiro por inteiro. É a âncora contra
alucinação — se o agente começar a divergir do estado real, este ficheiro
corrige-o.

**Regra de escrita:** depois de qualquer acção (mesmo pequena), actualizar
o ficheiro antes de terminar a resposta. Nunca deixar uma sessão terminar
sem o ficheiro reflectir o que mudou.

**Estrutura obrigatória do ficheiro (duas partes):**

**Parte A — ESTADO ACTUAL** (reescrita a cada actualização, reflecte a
verdade agora). Uma tabela ou lista, por directório/módulo, com:
- Caminho do ficheiro/função.
- O que faz (descrição curta).
- Estado: `✅ CONFIRMADO FUNCIONAL` | `⚠️ NÃO VERIFICADO` | `🔴 CONHECIDO
  COMO QUEBRADO` | `❌ NÃO EXISTE AINDA`.
- Última vez verificado, e como (que comando, que teste).

Esta parte é o "mapa do território" — cada ficheiro, cada rota de API, cada
componente de frontend, o que é responsável por quê. Quando um novo agente
(ou o mesmo, numa sessão futura) perguntar "o que faz este ficheiro", a
resposta está aqui, sem ter de ser redescoberta a ler código do zero de
cada vez.

**Parte B — JORNAL CRONOLÓGICO** (apenas acrescentado, nunca reescrito).
Uma entrada por acção relevante, datada:
```
### [DATA] — [O que foi feito]
- Ficheiros alterados: ...
- Porquê: ...
- Prova/teste realizado: ... (output real, não resumo)
- Resultado: funcionou / falhou parcialmente / falhou
- Segue-se: ...
```
Nunca apagar entradas antigas do jornal, mesmo que fiquem "ultrapassadas" —
se algo mudou de estado, escrever uma nova entrada a dizer isso, e
actualizar a Parte A. A história de como se chegou aqui é tão valiosa como
o estado actual, para perceber porque certas decisões foram tomadas.

SECÇÃO 11 — MAPA MENTAL INTERACTIVO 3D (NOVO REQUISITO — ESPECIFICAÇÃO)
--------------------------------------------------------------------------------

Além do `Mapa_Mental.md` textual (SECÇÃO 10), o agente deve criar e manter
um segundo artefacto: um mapa mental INTERACTIVO EM 3D, visual, que roda
LOCALMENTE (o agente de IA e o projecto correm no mesmo directório local —
não depende de nenhum serviço externo pago nem de publicação online).

**Objectivo:** dar ao fundador uma visão instantânea e visual de todo o
sistema — cada ficheiro/módulo do projecto como um ponto interligado no
espaço, com uma cor que comunica de imediato o seu estado real, sem
precisar de ler texto.

**Requisitos funcionais obrigatórios:**
1. Ficheiro único, auto-contido (HTML + CSS + JS embutidos, sem
   dependências externas que exijam rede — usar apenas bibliotecas locais
   ou CDN se realmente necessário, mas preferir tudo embutido para
   funcionar 100% offline), localizado em algo como
   `Mapa Mental/mapa_mental_3d.html`, aberto directamente no browser a
   partir do disco local (`file://`).
2. Renderização 3D interactiva: rotação, zoom, pan com o rato. (Pode usar
   uma biblioteca JS de grafos 3D leve, ou WebGL/Three.js simples — a
   escolha técnica fica ao critério do agente, desde que cumpra os
   requisitos funcionais.)
3. Cada NÓ (ponto) do grafo corresponde a UM ficheiro real dentro da
   estrutura de directórios do projecto (backend/, frontend/,
   admin-frontend/, etc.). O nome do nó é o caminho/nome do ficheiro.
4. Os nós estão LIGADOS entre si visualmente de acordo com as suas
   relações reais no sistema — por exemplo: um componente de frontend
   ligado ao endpoint de backend que consome; um endpoint ligado à tabela
   Prisma/BD que usa; um módulo funcional (ex: "Chenecas") ligado a todos
   os ficheiros (frontend + backend + serviço WhatsApp) que o compõem.
5. Cor de cada nó, segundo o ESTADO REAL e VERIFICADO do ficheiro (o mesmo
   estado que consta no `Mapa_Mental.md`, Parte A — nunca inventar um
   estado aqui que contradiga o Mapa Mental textual):
   - VERDE: 100% funcional, testado com prova real, e cuja lógica faz
     sentido para um programa real que vai lidar com dinheiro real (ex:
     cálculos de moeda correctos, isolamento de tenant garantido).
   - LARANJA: ainda em desenvolvimento / parcialmente implementado /
     implementado mas não verificado com prova.
   - VERMELHO: não faz sentido, lógica quebrada, ou não está a funcionar
     como deveria (bug confirmado).
6. Ao clicar ou passar o rato sobre um nó: mostrar um painel/tooltip com o
   caminho do ficheiro, descrição curta do que faz, estado, e a última
   verificação (mesmos dados da Parte A do Mapa_Mental.md) — não duplicar
   informação divergente, ler sempre a partir do mesmo `Mapa_Mental.md`
   como fonte de verdade (via leitura do ficheiro no momento da geração do
   HTML, não hardcoded manualmente sempre que possível).
7. Este ficheiro tem de ser REGENERADO (não apenas criado uma vez) sempre
   que o `Mapa_Mental.md` for actualizado de forma significativa — ou, no
   mínimo, sempre que uma mini-meta mudar o estado de algum ficheiro de
   🔴/⚠️ para ✅ ou vice-versa. Documentar no `Mapa_Mental.md` (Parte B,
   Jornal) sempre que o mapa 3D for regenerado.
8. Não é uma prioridade acima das regras de segurança e correcção
   funcional da SECÇÃO 7 e 8 — é uma ferramenta de visibilidade para o
   fundador, a construir/actualizar quando houver tempo disponível dentro
   de cada mini-meta relevante, nunca à custa de saltar REGRA 1 (paragem
   obrigatória) ou REGRA 3 (prova concreta).

SECÇÃO 13 — ANÁLISE CRÍTICA DETALHADA (todas as falhas encontradas na
auditoria, ordenadas por gravidade — "só apontar falhas, sem elogios, o
que é bom já está na SECÇÃO 12")
--------------------------------------------------------------------------------

**FALHA CRÍTICA 1 — Super Admin no mesmo frontend é um desastre de
segurança.**
O super admin é acessível em `/admin` no mesmo frontend React
(`<Route path="/admin" element={<AdminDashboard />} />`). Qualquer pessoa
que saiba o URL pode tentar brute force nessa rota. Por que é grave: expõe
a existência de um painel administrativo global a qualquer visitante; um
atacante com acesso ao JWT de um super_admin tem acesso a TODOS os
tenants; a separação no plano não é estética, é decisão de segurança
arquitectural; qualquer bot de scanning de rotas comuns encontra `/admin`
de imediato. O que o plano diz: `admin.genesis.co.mz` — subdomínio
separado ou URL completamente diferente. O que fazer: build React separada
ou subdomínio com middleware que rejeita qualquer pedido fora do domínio
correcto — não é uma mudança de uma linha, é separar fisicamente as duas
aplicações. (Ver estado em SECÇÃO 12.2, item 4 — parcialmente feito.)

**FALHA CRÍTICA 2 — Bug de moeda no OnboardingWizard (100x errado).**
`OnboardingWizard.jsx` usava `price_mzn`/`cost_mzn` directamente em MZN e
enviava assim para a API. A REGRA 6 (SECÇÃO 8) diz: dinheiro é inteiro,
nunca float, 150.50 MZN = 15050 centavos. Se o utilizador escreve 150.00
no campo de preço, o wizard envia 150 (não 15000) para o backend, que
espera centavos — 150 centavos = 1.50 MZN. O produto fica com preço de
1,50 MZN em vez de 150,00 MZN. Este bug apareceria logo no primeiro
onboarding de um cliente real: preços 100x menores, o proprietário vende a
1.50 MZN o que custa 150 MZN e tem prejuízo sem saber porquê. Correcção:
multiplicar por 100 antes de enviar (`Math.round(Number(p.price_mzn) *
100)`). (Estado: corrigido no wizard segundo SECÇÃO 12.1, mas confirmado
REPETIDO noutro ficheiro — SECÇÃO 12.2 item 2 — grep obrigatório em todo o
repositório.)

**FALHA CRÍTICA 3 — OnboardingWizard não era um wizard.**
Era uma página única com uma tabela de produtos, sem os 5 passos definidos
no plano (tipo de negócio → categorias adicionais → catálogo → custos
fixos/equipa → horário). Tipos de negócio disponíveis eram apenas
mercearia/restaurante/boutique — faltava justamente bottle_store, o
público-alvo número 1. Impacto: um novo cliente de bottle store não
encontra a sua categoria, escolhe "mercearia" por falta de opção, e recebe
um catálogo com arroz e açúcar em vez de cervejas e sumos — péssima
primeira impressão. (Estado: SECÇÃO 12.4 mostra como "parcialmente feito",
ver reescrita completa e lista de tipos correcta na SECÇÃO 6.1 e SECÇÃO
18.5.)

**FALHA CRÍTICA 4 — Owner Dashboard é um "Deus Componente" ingerível.**
`Owner/Dashboard.jsx` era um ficheiro monolítico com produtos,
fornecedores, stock, relatórios, PIN, tudo misturado — facilmente mais de
600 linhas num único componente React. Consequências: impossível
encontrar onde está o código de qualquer feature; cada nova feature torna
o ficheiro mais ilegível; bugs numa secção afectam as outras; testes
unitários impossíveis; qualquer IA (incluindo o próprio agente) tem
dificuldade em editar uma parte sem destruir outra. Correcção: dividir em
componentes separados conforme a árvore da SECÇÃO 5.4
(Products.jsx, Stock.jsx, Suppliers.jsx, Employees.jsx, Reports/*.jsx,
Debts.jsx, Cashiers.jsx, Goals.jsx, Settings.jsx).

**FALHA GRAVE 5 — Sem Route Guards (qualquer um acede a qualquer rota).**
`App.jsx` definia rotas mas não tinha `ProtectedRoute`. Qualquer pessoa
podia navegar directamente para `/owner`, `/admin`, `/pos` sem estar
autenticada. Um caixista podia escrever `/owner` na barra de endereços; o
backend rejeitaria as chamadas de API (JWT com role=cashier), mas o
frontend carregaria a página na mesma, mostrando erros e formulários que o
caixista não devia ver. (Estado: código do `ProtectedRoute.jsx` correcto
JÁ EXISTE — SECÇÃO 12.1 — mas coexiste com um `App.jsx` antigo sem
protecção nenhuma — SECÇÃO 12.2 item 1, CRÍTICO, resolver primeiro.)

**FALHA GRAVE 6 — Sem verificação de token expirado no carregamento.**
O login guardava o JWT num cookie httpOnly, mas ao carregar a app (ex:
utilizador abre o browser 25 horas depois) não havia lógica a verificar se
o token ainda era válido — o utilizador tentaria aceder a um endpoint,
receberia 401, e ficaria preso numa página com erro. Solução: hook
`useAuth` que, ao montar, chama `GET /api/auth/me` para validar o token;
se 401, limpar cookie e redirect para `/login`; se 200, injectar dados do
utilizador no estado global. (Código completo na SECÇÃO 18.3.)

**FALHA GRAVE 7 — QR Code nos recibos era um placeholder falso.**
`<div class="qr-box">QR</div>` — literalmente uma caixa com o texto "QR",
não um QR code real. Se escaneado, não funciona. Correcção: biblioteca
`qrcode` a gerar QR real com URL
`https://genesis.co.mz/verify/[sale_id]`. (Código completo na SECÇÃO
18.4.)

**FALHA GRAVE 8 — Nomes "LucroCerto" ainda podiam existir no código.**
O projecto foi renomeado para "Genesis" mas referências antigas ao
"LucroCerto" podiam persistir em comentários, variáveis, strings, ou nos
nomes de PDFs exportados (`LucroCerto_[tipo]_[data]_[nome-loja].pdf`).
Correcção: grep global por "LucroCerto"/"lucrocerto" em todo o
repositório e substituir por "Genesis"/"genesis".

**FALHA MODERADA 9 — Módulo de Chenecas completamente ausente no
frontend.** Schema da BD tem `debts` e `debt_payments`, backend
provavelmente tem endpoints, mas não havia interface no Owner Dashboard.
Esta é uma das funcionalidades mais diferenciadoras do produto.

**FALHA MODERADA 10 — Sem WhatsApp/Twilio em lado nenhum.** Zero código de

```javascript
// backend/src/middleware/adminOriginCheck.js
const ADMIN_ORIGINS = process.env.ADMIN_ORIGINS
  ? process.env.ADMIN_ORIGINS.split(',')
  : ['http://localhost:5175'];

module.exports = function adminOriginCheck(req, res, next) {
  const origin = req.headers.origin || req.headers.referer || '';
  const isAllowed = ADMIN_ORIGINS.some(o => origin.startsWith(o));
  if (!isAllowed) {
    return res.status(403).json({ error: 'Acesso negado: origin inválido' });
  }
  next();
};
// Aplicar em todas as rotas /api/admin/*
```

### 18.2 — ProtectedRoute.jsx + useAuth.js + endpoint /api/auth/me

```jsx
// frontend/src/components/ProtectedRoute.jsx
import React, { useEffect, useState } from 'react';
import { Navigate } from 'react-router-dom';
import api from '../utils/api';

const roleRedirects = {
  super_admin: '/admin-forbidden', // super admin não usa o frontend principal
  owner: '/owner',
  cashier: '/pos',
};

export default function ProtectedRoute({ children, requiredRole }) {
  const [status, setStatus] = useState('loading');
  const [userRole, setUserRole] = useState(null);

  useEffect(() => {
    api.get('/api/auth/me')
      .then(res => {
        const role = res.data.user.role;
        setUserRole(role);
        setStatus(!requiredRole || role === requiredRole ? 'ok' : 'wrong-role');
      })
      .catch(() => setStatus('unauthorized'));
  }, [requiredRole]);

  if (status === 'loading') return <LoadingSpinner />;
  if (status === 'unauthorized') return <Navigate to="/login" replace />;
  if (status === 'wrong-role') return <Navigate to={roleRedirects[userRole] || '/login'} replace />;
  return children;
}
```

```javascript
// frontend/src/hooks/useAuth.js
import { useState, useEffect } from 'react';
import api from '../utils/api';

export function useAuth() {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    api.get('/api/auth/me')
      .then(res => { setUser(res.data.user); setLoading(false); })
      .catch(err => { setError(err); setUser(null); setLoading(false); });
      // Se 401: cookie inválido/expirado — não faz redirect aqui,
      // o ProtectedRoute trata do redirect.
  }, []);

  return { user, loading, error };
}
```

```javascript
  const startDate = new Date(year, month - 1, 1);
  const endDate = new Date(year, month, 0, 23, 59, 59);

  const sales = await prisma.sale.findMany({
    where: { tenant_id: tenantId, status: 'completed', created_at: { gte: startDate, lte: endDate } },
    include: { sale_items: true }
  });

  const gross_revenue = sales.reduce((sum, s) => sum + Number(s.total_amount), 0);
  const cost_of_goods = sales.reduce((sum, s) =>
    sum + s.sale_items.reduce((si, item) => si + (Number(item.unit_cost_price) * Number(item.quantity)), 0), 0);
  const gross_profit = gross_revenue - cost_of_goods;

  const fixedCosts = await prisma.fixedCost.findMany({ where: { tenant_id: tenantId } });
  const total_rent = fixedCosts.filter(c => c.type === 'rent').reduce((s, c) => s + Number(c.amount), 0);
  const total_other_fixed = fixedCosts.filter(c => c.type !== 'rent').reduce((s, c) => s + Number(c.amount), 0);

  const employees = await prisma.employee.findMany({ where: { tenant_id: tenantId, is_active: true } });
  const total_salaries = employees.reduce((s, e) => s + Number(e.monthly_salary), 0);

  // Custo de fornecedores: entradas de stock REAIS no período, não "1x por fornecedor activo"
  const stockEntries = await prisma.stockEntry.findMany({
    where: { tenant_id: tenantId, created_at: { gte: startDate, lte: endDate }, supplier_id: { not: null } },
    include: { supplier: true }
  });
  const supplierDeliveryCosts = {};
  for (const entry of stockEntries) {
    if (entry.supplier_id && entry.supplier) {
      supplierDeliveryCosts[entry.supplier_id] = supplierDeliveryCosts[entry.supplier_id] ||
        { count: 0, cost_per_visit: Number(entry.supplier.delivery_cost_per_visit) };
      supplierDeliveryCosts[entry.supplier_id].count++;
    }
  }
  const total_supplier_delivery = Object.values(supplierDeliveryCosts)
    .reduce((s, sup) => s + (sup.count * sup.cost_per_visit), 0);

  const net_profit = gross_profit - total_salaries - total_rent - total_other_fixed - total_supplier_delivery;

  const revenue_by_payment = { cash: 0, mpesa: 0, emola: 0, pos_bank: 0 };
  for (const sale of sales) {
    revenue_by_payment[sale.payment_method] = (revenue_by_payment[sale.payment_method] || 0) + Number(sale.total_amount);
  }

  return {
    period: { year, month, startDate, endDate },
    sales_count: sales.length,
    gross_revenue, cost_of_goods, gross_profit,
    deductions: { total_salaries, total_rent, total_other_fixed, total_supplier_delivery },
    net_profit, // LUCRO LÍQUIDO REAL
    revenue_by_payment,
    employees_detail: employees.map(e => ({ name: e.name, role: e.role, salary: e.monthly_salary })),
    fixed_costs_detail: fixedCosts.map(c => ({ desc: c.description, amount: c.amount, type: c.type })),
  };
}
```

```javascript
const twilio = require('twilio');

async function sendWhatsApp(to, message) {
  if (!process.env.TWILIO_SID || process.env.TWILIO_SID.startsWith('placeholder')) {
```
